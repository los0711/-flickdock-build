# FlickDock Cloud

TypeScript Workers + D1 + private R2. Runtime/API/security details: ../CLOUD_SYNC.md.

Local: npm ci; npm run typecheck; npm test. Tests use isolated actual local workerd/D1/R2, no cloud credentials or emails. Integration covers auth challenges, Unicode uniqueness, R2-verified 3 MB single-part transfers, persisted static-WASM whole-file SHA256 for multipart, 65 MiB original-byte transfers, same-account instant reuse and last-reference deletion, commit/cancel races, device expiry, quotas and read leases.

Deployment is restricted to the authorized FlickDock account. wrangler.jsonc contains the dedicated non-secret D1 database ID and private bucket name. No source contains provider credentials. Provision AUTH_PEPPER (random >=32 chars) using wrangler secret put with stdin, apply migrations to the dedicated DB, then deploy. Never rotate AUTH_PEPPER after users exist without a deliberate account migration. This service does not enable Workers Paid or R2 public access. No separate 64 MiB/file cap; 8 GiB globally shared storage cap, provider quotas and monthly R2 API budgets remain. An exhausted provider quota suspends cloud requests until its reset while local shelf use continues. Committed files >500 MiB expire after 24 hours; local originals are kept. The final live reference deletion reclaims R2 objects and reserved space, with reader leases and scheduled retries. Existing clients retain 4 MiB single parts and 1 MiB multipart on Workers Free; updated clients opt in to the streamed fast path described below.

EMAIL_PROVIDER remains disabled. The production UI hides email binding at the user’s request. For a future free optional email binding, configure a verified sender domain via Resend, EMAIL_FROM, RESEND_API_KEY and random EMAIL_CODE_SECRET. For Cloudflare arbitrary-recipient Email Sending, the operator must first authorize/onboard the paid capability and sender domain; then add the EMAIL binding. No fake email success, test-recipient mail or registration verification.

The application sends derived password-equivalent auth material only over TLS; never log request bodies, authorization headers, codes, content or provider responses. Observability is disabled in config. Scheduled cleanup runs every 15 minutes and must be monitored. Authenticated password change requires the current password and a fresh device-bound challenge; the account verifier update and revocation of every other device are atomic. The current session remains signed in. This is password change, not recovery without the old password.

Pending uploads appear in the account-private `transfers` catalog before commit, including verified received bytes and the uploading device. `GET /v1/sync/changes` includes the same catalog, so clients need no extra polling request. Pending bytes are never exposed through content download endpoints. Cancel, commit and expiry remove the pending metadata; cancelling an in-flight R2 write reclaims its bytes as soon as the writer releases its lease. An identical original already stored by the same account creates a second item without sending its bytes again, and both items retain the content until the final live reference is deleted.

Updated clients explicitly opt in with `fast_upload: true`. For files up to 90 MiB, the Worker streams one request body to R2 with the file's SHA-256 as a storage checksum. This stays below the Workers Free 100 MB request-body limit without buffering the file or hashing 80 MiB within one Free CPU window. Updated clients request a single streamed original-byte download with `X-FlickDock-Fast-Content: 1`; older clients see a 1 MiB virtual range view and continue to work. A failed fast PUT or GET retries the whole file; larger files retain the resumable 1 MiB multipart protocol. Local workerd throughput is not a prediction of a user's internet speed. Run `bench_cloud_transfer_v188.py --allow-remote-usage --output <path>` only after deployment to measure the actual route with disposable 3 MB and 80 MiB data, SHA checks, and cleanup.

Manual cancellation retains an account-private UUID receipt for seven days. Initialization, status, part writes and commit return `410 UPLOAD_CANCELLED` for that UUID even after all R2 parts and allocations are removed. Cancelling an unknown UUID is idempotent and prevents a delayed initialization from reserving space; a database trigger closes the concurrent initialization race. Receipts do not block uploads in another account and are expired in bounded scheduled batches. An intentional retry starts a new upload UUID. Natural incomplete-upload expiry remains distinct from manual cancellation.
